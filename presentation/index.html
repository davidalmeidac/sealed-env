02 · El problema

Los archivos .env en texto plano dejaron de ser viables.

En toda app moderna hay un archivo .env con las contraseñas, llaves de API y URLs de bases de datos. El problema: es texto plano. Si alguien accede al disco, lo abre con cualquier editor.

Entre 2024 y 2026 vimos tres oleadas de ataques que demostraron que ese modelo está roto.

Sept · Nov 2025

Shai-Hulud

Un virus en npm que se replica solo y busca .env en cada máquina infectada.

Worm autorreplicante. Escaneaba el disco, encontraba .env, exfiltraba el contenido a repos públicos.

25,000+ repos comprometidos

Marzo 2025

tj-actions

Una herramienta de CI usada por miles de proyectos fue secuestrada para imprimir secrets en logs.

Atacante reescribió la versión publicada. Extraía secrets de la memoria del runner y los printeaba en logs públicos.

23,000+ proyectos afectados

Septiembre 2025

GhostAction

327 cuentas de GitHub comprometidas que enviaban todos los secrets de CI a un servidor del atacante.

Workflows con nombres legítimos POSTeaban el environment de CI completo a un servidor externo.

3,325 secrets · 817 repos · días

Hace falta cifrar el archivo en disco — y abrirlo solo cuando toca, en el lugar que toca.

03 · La solución

sealed-env

La metáfora exacta es una carta lacrada. Como hacían los romanos: la carta se cierra, se aplica cera caliente, se presiona un sello (sigillum) que solo el dueño tiene. Cualquiera puede ver la carta sellada en el camino, pero solo abriéndola con la llave correcta — y rompiendo el sello — se lee el contenido.

sealed-env hace lo mismo con tu archivo .env: lo cifra con criptografía moderna, te deja commitearlo a git tranquilamente, y solo se abre cuando tu app arranca con la llave correcta.

  • Cifrado
    AES-256-GCM
  • Derivación de clave
    Argon2id · scrypt
  • Subclaves
    HKDF-SHA256 (RFC 5869)
  • Integridad
    HMAC-SHA256
  • 2do factor
    TOTP (RFC 6238)
  • Wire format
    SEALED-ENV-V1 · spec abierta
  • Distribución
    npm · Maven Central · GPG-signed

Tres niveles de seguridad

basic — un dev solo, una llave maestra. Suficiente para proyectos pequeños.

team — añade firma de integridad. Detecta si alguien modificó el archivo.

enterprise — añade 2 factores: para hacer deploy, el operador necesita su llave maestra y un código de 6 dígitos de su Google Authenticator. Cada deploy genera un permiso temporal de 60 segundos.

04 · Quién tiene qué

El operador descifra. El servidor solo recibe lo que necesita.

La idea clave: las llaves nunca tocan el servidor. El operador (la persona que hace el deploy) tiene las llaves en SU laptop. El servidor solo recibe los valores ya descifrados — únicamente lo que la app necesita para correr. Si alguien hackea el servidor, no consigue las llaves; consigue solo los datos del deploy actual.

El operador

Laptop · OS keychain

  • ●Llave maestra
  • ●Llave de firma
  • ●Secret de TOTP (Google Authenticator)
  • ●Genera el permiso temporal en RAM
  • ●Descifra el archivo en RAM
Solo plaintext env vars

El servidor

Container · producción

  • ●$DATABASE_URL & demás env vars de la app
  • ○NO tiene la llave maestra
  • ○NO tiene la llave de firma
  • ○NO tiene el TOTP secret
  • ○NO tiene el permiso temporal

Si el servidor se compromete, el atacante ve los valores de este deploy. No puede generar permisos nuevos. No puede leer archivos pasados ni futuros. No escala.

05 · El flujo de un deploy

Qué pasa, paso a paso

En modo enterprise, cada vez que se hace un deploy a producción el operador tipea un código de 6 dígitos de su autenticador. Eso autoriza la creación de un permiso temporal que solo dura 60 segundos y solo sirve para ese deploy específico. Si el permiso se filtra, expira solo y no sirve para deploys futuros.

07 · La historia del bug crítico en mi propia librería

Cuatro horas · de reporte a fix publicado

GHSA-x3r2-fj3r-g5mv

Un revisor externo encontró que el permiso temporal contenía dentro de sí el TOTP secret completo. El permiso es texto firmado pero no encriptado — cualquiera que lo viera (en un log, en un dump del servidor) podía sacar el secret y generar permisos nuevos para siempre. Bug crítico en mi propia lib de seguridad.

"El payload del permiso es base64, no encriptado. Cualquiera con acceso al token (logs de CI, dump del container) puede extraer el TOTP secret y generar permisos nuevos para deploys futuros indefinidamente."

08 · Lo que aprendí

Tres lecciones que documenté en el threat model

I

Un permiso firmado no es un permiso encriptado.

JWT y JWS — los tokens más usados en la web — están firmados, no encriptados. La firma asegura que nadie los modifique, pero su contenido es público. Es un error de diseño común y fácil de cometer bajo presión cuando tu verificador "necesita" el secret para validar.

II

Llevá huellas, nunca los originales.

El fix: en lugar de meter el TOTP secret en el permiso, meto una huella criptográfica ligada al archivo. La huella sirve para validar el permiso, pero no permite reconstruir el secret original. Si el permiso se filtra, la huella es inútil para deploys futuros.

III

Probá lo que NO querés que pase.

Los tests ahora aseveran ausencias: el permiso NO contiene el secret literal en ninguna codificación (hex, base64, base32). Las aserciones negativas atrapan regresiones de diseño que las positivas no ven nunca.

09 · Velocidad de iteración

De "librería que funciona" a "librería con la que es agradable trabajar". Cada release respondió a fricción real (mía, dogfoodando) o a feedback externo. La alpha.4 fue el fix de seguridad crítico.
